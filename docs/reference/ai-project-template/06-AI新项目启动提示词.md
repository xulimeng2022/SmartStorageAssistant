# AI 新项目启动提示词

将下面提示词中的【占位内容】替换后发送给 AI。首次只让 AI 做文档和拆分；不要在需求与范围未确认前让它直接开始写代码。

## A. 让 AI 生成新项目知识库骨架

~~~text
你是我的 AI 开发协作者。请基于以下已确认的信息，为一个新项目建立 Obsidian 项目知识库。

【项目名称】：…
【一句话目标】：…
【目标用户】：…
【客户要解决的问题】：…
【本期必须功能】：…
【明确不做】：…
【使用环境/技术约束】：…
【交付物】：…
【已知数据、接口或合规要求】：…
【待确认事项】：…

请只输出以下内容：
1. 项目索引：项目目标、当前阶段、模块导航和新会话阅读顺序。
2. 需求与范围确认：将功能转为可验收的用户场景，保留所有待确认项。
3. 系统架构：模块边界、模块依赖、主要数据流；不要虚构技术、接口或数据表。
4. 模块清单：每个模块的一句话职责、输入/输出、明确不负责什么。
5. Todo：拆为可独立完成、可测试、可验收的任务，并标明依赖。

要求：
- 需求不明确时标记「待确认」，不要自行补全。
- 「本期不做」必须单列，不能混入任务。
- 每个任务只解决一个可观察的行为。
- 模块文档只记录稳定设计；临时日志、账号、客户真实数据、凭据和截图不得写入。
- 先交付 Markdown 文档草案，等待我确认后再提出实现计划。
~~~

## B. 开启一个模块开发对话

~~~text
你现在只负责【模块名称】中的任务【T-编号：任务名称】。

请只阅读：
- 项目索引：…
- 需求与范围：…
- 系统架构：…
- 当前模块文档：…
- 当前任务卡：…
- 相关代码和现有测试：…

任务目标：…
不做范围：…
验收标准：…

工作规则：
1. 若需求、模块边界或验收存在歧义，先指出具体问题，停止猜测。
2. 先写一个会失败的测试，准确描述目标行为；说明它为什么应该失败。
3. 再实现最小改动使测试通过，不顺手重构无关代码。
4. 运行受影响测试，报告测试结果和改动文件。
5. 只在有长期价值时，建议将哪些结论回写到模块文档。
~~~

## C. 让 AI 排查一个 Bug

~~~text
你现在只排查【模块名称】中的 Bug：【现象】。

边界：
- 关联模块文档：…
- 预期行为：…
- 实际行为：…
- 最小复现步骤：…
- 已有测试/错误信息：…
- 本次不改动的范围：…

请按顺序输出：
1. 从当前模块、调用链和已有测试中可确认的事实。
2. 最可能的根因与证据；无法确认时明确需要什么信息。
3. 一个最小修复方案与要新增/调整的失败测试。
4. 不要直接扩大到其他模块或加入无依据的兜底逻辑。
~~~

## D. 任务完成后的知识库回写提示词

~~~text
请根据已完成任务【T-编号】和验证结果，区分：
- 应写入长期知识库的稳定事实：模块边界、接口契约、状态定义、架构决策、可复用待办。
- 不应写入长期知识库的短期信息：日志、命令输出、真实业务数据、账号凭据、截图和一次性回执。

只输出建议更新的笔记名称、具体段落和 Markdown 草案；没有长期结论就明确写「无需回写」。
~~~
