## 版本规则
- 日常开发（功能 / 修复 / 重构 / UI / 资源 / 配置 / 依赖变更）不得自动递增版本号；只有 Release 阶段或用户明确要求时才更新，见根目录 `AGENTS.md`「版本号规则」与 `PROJECT_STATUS.md`。
- 每次发版 versionCode 必须大于上一版（Android 升级判定）。

## 构建与交付策略
- Debug 只用于开发、快速验证、编译检查、UI 调试、Logcat、异常定位、断点调试、回归测试和 Codex 诊断；可以按需执行，但默认不复制、不归档、不交付。
- Release 是默认的用户交付产物。直接安装、用户真机验收、阶段验收、RC、GitHub、网盘和正式分发默认使用 Release APK；应用商店要求 AAB 时使用 Release AAB。
- 只有用户明确要求 Debug APK 做特殊诊断时，才允许把 Debug APK 作为例外交付物；报告必须明确这是显式请求。
- 不为“流程完整”重复执行无意义构建。Release 仅在用户验收、Release-only 问题排查、阶段验收、正式发布或任务明确要求时执行。

| 场景 | 构建 / 验证 | Final user-facing artifact |
| --- | --- | --- |
| 开发、修复、诊断、自动验证 | Debug 按需 | None |
| Release-only 问题排查 | 模块工作树可执行 Debug / Release 对照验证 | None；除非 Coordinator 另行转为正式验收 |
| 用户安装包、真机验收、阶段验收、RC | Release APK | Release APK |
| GitHub、网盘、直接分发 | Release APK | Release APK |
| 应用商店要求 AAB | Release AAB | Release AAB |
| 同一任务需要多个渠道 | 只生成实际需要的 APK / AAB | 对应渠道的 Release APK / AAB |

## 构建命令与产物
| 类型 | 命令 | 产物与定位 |
| --- | --- | --- |
| Debug | `.\gradlew.bat :app:assembleDebug` | `app\build\outputs\apk\debug\app-debug.apk`；内部验证，不默认交付 |
| Release APK | `.\gradlew.bat :app:assembleRelease` | `app\build\outputs\apk\release\app-release.apk`；默认用户交付产物 |
| Release AAB | `.\gradlew.bat :app:bundleRelease` | `app\build\outputs\bundle\release\app-release.aab`；仅在应用商店明确要求时使用 |

- 当前项目常规分发仍以 Release APK 为准；AAB 规则只用于未来应用商店渠道，不表示每次发布都要同时生成 APK 和 AAB。
- Release 开启 R8 混淆与资源压缩（`isMinifyEnabled` / `isShrinkResources`），规则在 `app/proguard-rules.pro`。
- 混淆映射文件位于 `app\build\outputs\mapping\release\mapping.txt`，正式 Release 必须随版本归档到 `release/<版本>/mapping.txt`。

## Release 构建前检查
构建前读取实际配置，不得假设项目一定启用某项能力：
- `versionName`、`versionCode`。
- Release signing、keystore 和 `local.properties` 签名四键是否完整。
- `isMinifyEnabled`、`isShrinkResources`、ProGuard / R8 规则。
- BuildConfig、Manifest 和 release-specific 配置差异。
- Build Variant、ABI / splits 配置。
- 产物类型：APK、AAB，或本次任务确实需要两者。

- 签名配置优先沿用项目现有正式方案，不创建新签名体系、不覆盖 keystore、不把 keystore 或密码写入仓库。
- 签名缺失时可以构建未签名 Release 用于内部 R8 / 功能验证，但不得把未签名产物作为正式用户交付物或发布物。

## Debug 与 Release 差异排查
出现 Debug 正常但 Release 崩溃、功能失效、网络异常、反射 / JSON / 序列化失败、模型被裁剪或 UI / 资源异常时，优先检查：
- R8 / ProGuard 规则和 mapping。
- resource shrinking。
- BuildConfig、Manifest 和 release-specific 配置。
- 签名与安装包差异。

UI / Data / AI 模块工作树可以直接执行 Release 构建来完成上述排查，不需要把验证工作转交 Coordinator；但该构建仅用于诊断，不代表正式交付或发布。Debug 构建成功不能代替 Release 验证。

## 签名（只记录位置与规则，不记录值）
- 签名配置在 `app/build.gradle.kts` 的 release 构建类型，从根目录 `local.properties` 读取 `KEYSTORE_FILE / KEYSTORE_PASSWORD / KEY_ALIAS / KEY_PASSWORD`；未配置则产出未签名包。
- 密钥库文件（`*.jks` / `*.keystore`）已被 `.gitignore` 忽略，严禁提交；`local.properties` 同样不入库。
- 密钥丢失后无法对已发布 App 升级签名，需妥善备份（见 `RELEASE_GUIDE.md`）。

## 正式 Release 流程
1. Coordinator 确认分发渠道和产物类型：直接安装 / GitHub / 网盘使用 Release APK，应用商店需要 AAB 时使用 Release AAB；只生成实际需要的类型。
2. 确认 `versionName / versionCode`、签名和实际 Release 构建配置。
3. 生成所需 Release 产物，保存 `mapping.txt` 并归档。
4. 核验产物类型、版本、签名、大小、SHA-256 和 mapping。
5. 执行核心功能验证和 Release APK 真机验收；AAB 按对应应用商店测试渠道验证。
6. 确认更新说明和最终产物。
7. 获得用户明确授权后，才执行 Push / Tag / GitHub Release / 网盘分发 / 应用商店上架。

## 产物元数据
- Release APK：versionName、versionCode、文件名、路径、大小、SHA-256、签名状态。
- Release AAB：versionName、versionCode、文件名、路径、大小、SHA-256、签名状态、对应分发渠道。
- 默认不列出 Debug APK 路径；只有用户明确要求 Debug 诊断包时才作为例外交付。
